# ASD Chatbot — النسخة المحسّنة (v2)

هذا هو نفس مشروع التخرج، لكن بعد إعادة هيكلة الباك-إند بالكامل، نقل قاعدة
البيانات إلى **Supabase (PostgreSQL)**، وإضافة مجموعة اختبارات آلية.

## أهم الإصلاحات التي تمت

1. **خطأ جوهري في الجلسات (Session Bug):** الكود القديم كان يخزّن `userId` و
   `conversationId` في متغيرات عامة (`let userId; let conversationId;`)
   على مستوى السيرفر بأكمله. هذا يعني أنه إذا استخدم شخصان التطبيق في نفس
   الوقت، محادثة أحدهما تُخزَّن باسم الآخر! تم استبدال هذا بـ
   `express-session` بحيث كل مستخدم له جلسة مستقلة (كوكي خاص به).
   يوجد اختبار مخصص لهذه النقطة بالذات في `tests/app.test.js`.
2. **كلمات المرور كانت تُخزَّن نص عادي (plain text)** في قاعدة البيانات
   وتُقارَن بـ `=` مباشرة في SQL. الآن تُشفَّر بخوارزمية `scrypt` (عبر
   وحدة `crypto` المدمجة في Node، فلا حاجة لتثبيت مكتبة خارجية).
3. **حقن SQL (SQL Injection):** بعض الاستعلامات القديمة كانت آمنة جزئياً
   (parameterized) لكن الطريقة العامة غير متّسقة. مع Supabase
   query-builder الجديد كل القيم تُمرَّر كمعاملات دائماً.
4. **مسار مكسور فعلياً:** الواجهة الأمامية (`script.js`) كانت تنادي
   `/createConversationChild` (بحرف C كبير) في مكان، و
   `/createConversationchild` (بحرف c صغير) في مكان آخر، بينما السيرفر
   القديم عرّف فقط النسخة بحرف صغير — فيصبح النداء الأول 404 دون أن
   يلاحظ أحد. الآن كلا المسارين يعملان.
5. **دالة غير موجودة:** `/insertConversation` كان يستدعي
   `getUserIdFromMemory()` وهي دالة غير مُعرَّفة أصلاً (كانت ستُسقِط
   الطلب بخطأ 500 دائماً). تم إصلاحها لتستعمل الجلسة.
6. **مفتاح Gemini API كان مكتوباً صراحةً داخل ملف `.env` المرفوع** ضمن
   الأرشيف. تم حذفه ويجب عليك توليد مفتاح جديد (انظر الخطوات أدناه) لأن
   المفتاح القديم يجب اعتباره مكشوفاً.
7. تم تفعيل `Row Level Security` على كل الجداول في Supabase، مع عدم وجود
   أي "policy" — أي أن أي طلب يستخدم المفتاح العام (anon key) لا يمكنه
   قراءة/كتابة أي شيء؛ فقط الباك-إند (بمفتاح service_role السرّي) يقدر.

## هيكلة المشروع

```
chatbot-app/
├── server.js                  # نقطة الدخول (يشغّل السيرفر الحقيقي)
├── server/
│   ├── app.js                 # كل الـ routes (Express) بدون أي اتصال مباشر بقاعدة بيانات حقيقية
│   ├── repository.js          # طبقة الوصول لقاعدة بيانات Supabase
│   ├── supabaseClient.js      # إنشاء عميل Supabase
│   ├── geminiChat.js          # الاتصال بـ Gemini API
│   └── passwords.js           # تشفير/تحقق كلمات المرور
├── db/
│   └── schema.sql             # مخطط قاعدة البيانات الجديد (Postgres/Supabase)
├── public/                    # نفس الواجهة الأمامية القديمة (HTML/CSS/JS) مع إصلاحات بسيطة
├── tests/
│   ├── app.test.js            # اختبارات آلية تعمل بدون إنترنت (تستخدم قاعدة بيانات وهمية بالذاكرة)
│   ├── fakeRepository.js
│   ├── testServer.js
│   └── checkSupabaseConnection.js  # اختبار حقيقي يتصل بمشروع Supabase الفعلي
├── .env.example
└── package.json
```

## خطوة بخطوة: الإعداد

### 1) إنشاء مشروع Supabase
1. اذهب إلى https://supabase.com وأنشئ حساباً/مشروعاً جديداً (مجاني).
2. من **SQL Editor** داخل لوحة تحكم Supabase، افتح استعلاماً جديداً،
   الصق محتوى الملف `db/schema.sql` بالكامل، ثم اضغط Run.
   هذا سينشئ كل الجداول (`users`, `children`, `conversations`, `messages`,
   `asd_metrics`, `asd_analysis`) مع الفهارس والقيود، ويُفعّل RLS.
3. من **Project Settings → API** خذ:
   - `Project URL` → `SUPABASE_URL`
   - `service_role secret key` → `SUPABASE_SERVICE_ROLE_KEY`
   ⚠️ لا تستعمل أبداً مفتاح `service_role` في كود يعمل على المتصفح، فقط
   على السيرفر (وهو بالضبط ما يفعله هذا المشروع).

### 2) متغيرات البيئة
```bash
cp .env.example .env
```
ثم عدّل `.env` وضع فيه:
- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`
- `GEMINI_API_KEY` (احصل على مفتاح جديد من https://aistudio.google.com/apikey
  لأن المفتاح القديم في المشروع الأصلي كان مكشوفاً في الأرشيف المرفوع)
- `SESSION_SECRET` (أي نص عشوائي طويل)

### 3) تثبيت الاعتماديات وتشغيل المشروع
```bash
npm install
npm start
```
افتح المتصفح على http://localhost:4000

### 4) اختبار الاتصال الحقيقي بـ Supabase
```bash
npm run check:supabase
```
هذا السكربت يقوم بعملية إدراج/قراءة/حذف حقيقية على جدول `users` في
مشروعك على Supabase، ليؤكد أن كل شيء متصل فعلاً قبل تسليم المشروع.

> **ملاحظة مهمة بخصوص بيئة العمل التي استعملتها لتحضير هذا التسليم:**
> بيئة التنفيذ الخاصة بي هنا لا تملك اتصالاً بالإنترنت (الشبكة معطّلة
> بالكامل)، لذلك لم أستطع إنشاء مشروع Supabase حقيقي أو تشغيل
> `npm run check:supabase` أو حتى `npm install` بنفسي لتنزيل حزمة
> `@supabase/supabase-js`. ما فعلته بدل ذلك هو:
> - كتابة كل منطق التطبيق (`server/app.js`) بشكل مستقل تماماً عن أي
>   مكتبة اتصال حقيقية (عبر حقن `repo` و`runChat` كوسيطين)،
> - بناء قاعدة بيانات وهمية في الذاكرة (`tests/fakeRepository.js`)
>   ومحاكي Gemini، وتشغيل **9 اختبارات تكامل حقيقية** ضدهما (تسجيل
>   دخول/تسجيل حساب/محادثة/حفظ طفل...) وقد نجحت كلها فعلياً في بيئتي:
>   `npm test` أعطى `9 pass, 0 fail`.
> - تجهيز `db/schema.sql` و`server/supabaseClient.js` و
>   `tests/checkSupabaseConnection.js` بشكل جاهز تماماً للعمل بمجرد أن
>   تُدخل بيانات مشروعك الحقيقي على Supabase — لكن يجب عليك أنت تشغيل
>   الخطوة 4 أعلاه بنفسك (تأخذ دقيقتين) للتأكد النهائي قبل التسليم،
>   لأنني لا أملك طريقة لأتحقق من اتصال شبكي فعلي من هنا.

## تشغيل الاختبارات الآلية (لا تحتاج إنترنت ولا Supabase حقيقي)
```bash
npm test
```
يجب أن تظهر لك النتيجة: `# pass 9` و `# fail 0`.
هذه الاختبارات تغطي: التسجيل، تسجيل الدخول (كلمة مرور صحيحة/خاطئة)،
عزل الجلسات بين مستخدمين مختلفين (الخطأ الأساسي في النسخة القديمة)،
تدفق المحادثة الكامل، حفظ الأطفال، والمسارين المتضاربين
`createConversationChild` / `createConversationchild`.

## ما لم يتغيّر عمداً
- شكل الواجهة الأمامية (HTML/CSS) لم يُعَد تصميمه، فقط أُصلحت الأخطاء
  البرمجية والوظيفية.
- أسماء الـ endpoints بقيت كما هي قدر الإمكان حتى تبقى الواجهة الأمامية
  متوافقة دون الحاجة لإعادة كتابتها بالكامل.

## نقاط يُنصح بتطويرها لاحقاً (اختيارية)
- استبدال `express-session` (تخزين في الذاكرة) بتخزين جلسات في Supabase
  نفسه أو Redis إذا كان المشروع سيُنشر بعدة نسخ من السيرفر (production).
- إضافة `helmet` و`rate limiting` لحماية إضافية.
- الجدول `asd_analysis` غير مستخدم فعلياً في أي route حالياً (كان كذلك
  في الأصل أيضاً) — تُرك في المخطط للتوافق فقط.
